# データスキーマ・EDINET＋LLMパイプライン＆データ管理仕様書

## 1. 配信用分割JSON設計（GitHub Pages 静的配信）

全上場企業（約1,600〜3,800社）を無料かつ高速に配信するため、静的JSONを役割別に分割して `public/data/` へ出力する。既存の単一JSON（`src/data/sample.json`）スキーマとも後方互換性を維持する。

| ファイルパス | 想定サイズ（gzip後） | 内容・用途 | 読込タイミング |
| --- | --- | --- | --- |
| `public/data/meta.json` | ~1 KB | 最終更新日時、収録企業数、エッジ数、対象決算期、データ種別（`sample` / `live`） | 起動時 |
| `public/data/index.json` | ~100〜200 KB | 全上場企業の軽量検索インデックス（`code`, `name`, `sector`, `market`, `marketCap`, `capital`, `degree`） | 起動時（検索用） |
| `public/data/core.json` | ~50〜100 KB | 初期表示用コアグラフ（時価総額・次数上位の主要ハブ約150〜200社＋主要エッジ） | 起動時（即座に3D描画） |
| `public/data/network.json` | ~300〜700 KB | 全上場企業のノード基本情報＋全関係エッジ（抜粋テキストは含めず軽量化） | コア外検索・全社モード切替時に遅延読込 |
| `public/data/details/{0-9}.json` | 各 ~50〜150 KB | 証券コード先頭1桁で10分割した企業詳細（有報抜粋・LLM抽出根拠・提出日・`docId`） | ノード選択時に該当バケットのみ読込＆キャッシュ |

> **フォールバック挙動**：`public/data/core.json` が未生成の開発段階や読込失敗時は、自動的に同梱の `src/data/sample.json` へフォールバックする。

## 2. ネットワークJSONスキーマ（拡張契約）

既存 [README.md](../README.md) の必須フィールドをすべて維持しつつ、全上場＆ハイブリッド抽出に必要な任意フィールドを追加する。

### 2.1 `nodes`（企業）

| フィールド | 型 | 必須 | 説明 |
| --- | --- | --- | --- |
| `id` | string | 必須 | 一意識別子（4桁証券コード。非上場主要取引先を扱う場合は `U:<正規化名>` 等） |
| `code` | string | 必須 | 証券コード（4桁。英字入り新コード例 `130A` もそのまま文字列保持） |
| `name` | string | 必須 | 企業名（正規化済みの表示名） |
| `sector` | string | 必須 | 業種・セクター名（JPX 33業種または集約セクター。色分け単位） |
| `marketCap` | number | 必須 | 時価総額（兆円。未取得時は `0`） |
| `capital` | number | 必須 | 資本金（兆円。未取得時は `0`） |
| `logo` | string | 必須 | ロゴ画像URL（取得不可時はUI側で略称バッジにフォールバック） |
| `logoText` | string | 任意 | ロゴ代替の英字・カナ略称 |
| `market` | string | 任意 | 東証市場区分（`プライム` / `スタンダード` / `グロース`） |
| `edinetCode` | string | 任意 | EDINETコード（例：`E02144`） |
| `fiscalYear` | string | 任意 | 取得元有報の決算期（例：`2025-03`） |
| `excerpt` | string | 任意 | 有報テキスト要約（`details/*.json` 側へ分離格納も可） |

### 2.2 `links`（企業間の関係）

| フィールド | 型 | 必須 | 説明 |
| --- | --- | --- | --- |
| `source` | string | 必須 | 関係元ノード `id` |
| `target` | string | 必須 | 関係先ノード `id` |
| `value` | number | 必須 | 関係値 `0〜100`（線の太さ・粒子・フィルタ基準） |
| `kind` | string | 必須 | 関係種別：`主要顧客・供給` / `政策保有株式` / `大株主` / `資本・業務提携` / `供給網・リスク` |
| `sourceType` | `"table" \| "llm"` | 任意 | 抽出元の種別（`table`＝有報定型表ルールベース、`llm`＝LLM本文抽出） |
| `detail` | string | 任意 | 補足テキスト（例：`売上構成比 38.2%（4,210億円）` / `保有株式 1.2億株`） |
| `amountMillionYen` | number | 任意 | 定型表から取得した金額（百万円） |
| `ratioPercent` | number | 任意 | 売上構成比・持株比率（%） |
| `docId` | string | 任意 | 出典のEDINET書類管理番号（例：`S100XXXX`） |

## 3. EDINET＋LLMハイブリッド抽出パイプライン

### 3.1 パイプライン全体ステップ

```
[Step 1] マスタ同期（無料）
  - EDINETコードリストCSV（EDINETコード ⇄ 証券コード ⇄ 提出者名）
  - JPX上場銘柄一覧Excel（証券コード ⇄ 市場区分 ⇄ 33業種/17業種）
  - Google Sheets 名寄せ例外辞書（任意・存在すればマージ）
        │
[Step 2] EDINET差分取得（無料・EDINET API v2）
  - 対象期間の提出日を走査し、有価証券報告書（docTypeCode="120"）をリストアップ
  - 取得済みマニフェスト（docId単位）と突合し、未処理の最新有報のみZIPダウンロード
  - ZIPは処理後に破棄または一時キャッシュ（リポジトリには一切含めない）
        │
[Step 3] iXBRL定型表パーサ（ルールベース・無料・高精度）
  - PublicDoc配下の iXBRL (.htm) を BeautifulSoup / lxml で解析
  - 抽出対象：
      1) 「主要な顧客ごとの情報」テーブル → 相手先・売上金額・割合
      2) 「特定投資株式（政策保有株式）」テーブル → 銘柄名・株式数・BS計上額・保有目的
      3) 「大株主の状況」テーブル → 法人大株主名・持株比率
  - 同時にLLM入力用の対象セクション本文（事業等のリスク、経営上の重要な契約、MD&A等）を軽量テキスト化
        │
[Step 4] LLM本文抽出（Gemini API 無料枠・docIDキャッシュ）
  - 未抽出の docId のみ、1回の実行上限（無料枠RPD以内）でバッチ処理
  - Structured Output（JSON Schema強制）で「相手企業名・関係種別・強度目安・根拠1行抜粋」を抽出
  - 抽出済みJSONを docId 単位でキャッシュし、同じ有報へ二重課金・二重実行しない
        │
[Step 5] 自動名寄せ＆関係値スコア統合
  - 企業名正規化（全角/半角、株式会社/㈱除去、空白統一、旧社名・略称辞書）
  - EDINET/JPXマスタ＋Sheets例外辞書で証券コードへマッピング（未一致はログ出力）
  - 同一ペア・複数ソースのエッジを集約し、関係値 value (0〜100) を正規化算出
        │
[Step 6] 時価総額付与＆分割JSON出力
  - yfinance 等で上場企業の時価総額を一括更新（取得失敗時は前回値を保持して欠損防止）
  - public/data/{meta,index,core,network,details/*}.json を生成し、GitHub Pagesへ反映
```

### 3.2 関係値（`value`: 0〜100）の算出基準案

| 関係種別 | 算出ルール（初期案） |
| --- | --- |
| `主要顧客・供給` | 売上割合（%）ベース：`min(100, max(20, round(ratio * 2.5 + 25)))`（例：10%→50、30%→100） |
| `政策保有株式` | BS計上額の対数スケール（例：10億円→35、100億円→65、1,000億円以上→95） |
| `大株主` | 持株比率（%）ベース：`min(100, max(25, round(ratio * 2 + 20)))` |
| `資本・業務提携` / `供給網・リスク`（LLM） | LLMの確信度・重要度（低=35 / 中=60 / 高=80）に上限を設け、定型表の定量関係より過大評価されないよう調整 |

## 4. 完全無料運用（Git / GitHub Actions / Google Sheets / Drive の役割分担）

| ストレージ / 実行基盤 | 役割 | コスト | 肥大化・遅延対策 |
| --- | --- | --- | --- |
| **GitHub リポジトリ & Pages** | ソースコード、仕様書、配信用分割JSON（`public/data/`）の正本・CDN配信 | 無料 | 生XBRL・巨大ZIPは `.gitignore`。配信JSONは分割＋抜粋分離で軽量維持 |
| **GitHub Actions** | ① 日次／週次の新着有報取得＆定型表パース＆時価総額更新<br>② LLM本文抽出の無料枠内トリクル消化（1日数十〜数百件ずつ処理しバックログ完了後は新着のみ） | 無料（パブリックリポジトリ） | `docId` 単位の増分処理。中間抽出キャッシュはActionsキャッシュまたはDrive/ブランチで保持 |
| **Google Sheets** | 人間が確認・介入する軽量マスタのみ：<br>① `alias_overrides`（名寄せ例外辞書：原文→証券コード）<br>② `unmatched_log`（名寄せ漏れ上位リスト）<br>③ `batch_status`（最終実行・抽出件数サマリー） | 無料 | 全3,800社の生エッジは入れない（軽量に保つ） |
| **Google Drive** | 大容量の中間抽出キャッシュ（`docId` 毎の抽出JSONアーカイブ）や必要時の原本ZIP退避先 | 無料（15GB枠） | 圧縮済み抽出JSONのみ保存すれば3,800社でも数百MB以内に収まる |

### 必要なシークレット（GitHub Actions Secrets）
- `EDINET_API_KEY`（必須・無料）：EDINET閲覧サイトで発行した Subscription-Key
- `GEMINI_API_KEY`（Phase 4で任意・無料枠あり）：Google AI Studio で発行したAPIキー（未設定時は定型表のみで自動スキップ動作）
